## Context

The current editor supports ten printable element types, runtime JSON binding, a local/REST template repository, and browser printing.  Its template library only lists saved documents, the element-preset action is intentionally a placeholder, and property schemas are uneven across element types.  Page settings and runtime rendering also need an explicit shared property contract before adding more controls.

This work is a commercial independent implementation.  The reference product may inform feature categories only; no source code, template JSON, copy, brand asset, screenshot, or visual layout is an implementation input.

## Goals / Non-Goals

**Goals:**

- Make common independent starter templates quick to discover and instantiate.
- Keep every saved, imported, and inserted template/preset normalized as `TemplateDocument v1` data.
- Provide a complete, validated property surface for the currently supported elements and pages.
- Make multi-selection layout commands deterministic, undoable, and independent of viewport state.
- Preserve output parity: editor configuration, runtime preview, and browser print consume the same persisted properties.

**Non-Goals:**

- Add PDF, silent, cloud, or server-side printing.
- Add upstream template assets, naming, visual designs, or import compatibility for upstream proprietary/export formats.
- Add arbitrary JavaScript execution to property expressions or table transformations.
- Add new complex element categories (for example rich text, SVG paths, charts, or freehand drawing) in this change.
- Add remote sharing, collaborative editing, access control, or backend template APIs beyond the existing repository boundary.

## Decisions

### 1. Use declarative first-party starter definitions, not saved-document seed data

Starter templates will be code-owned declarative definitions with stable catalog IDs, metadata, a thumbnail generated by local UI/CSS, and a fresh `TemplateDocument v1` factory.  Instantiation will generate new document/page/element IDs and strip catalog-only metadata.  Starter templates are never silently inserted into the user repository.

Alternative considered: ship pre-saved documents in browser storage.  Rejected because those records can be overwritten by users, cannot be safely versioned, and blur the difference between a catalog definition and a user document.

### 2. Define a portable interchange envelope around `TemplateDocument v1`

Export will produce JSON with an interchange identifier, format version, exported timestamp, and a normalized template.  Import will parse only JSON, validate the envelope and document, migrate supported legacy aliases, and report field-level errors without replacing the active document until the import is valid.  Unsupported format versions fail explicitly.

Alternative considered: export the editor store snapshot.  Rejected because it leaks selection/history/zoom state and violates the existing runtime contract.

### 3. Store reusable element presets separately from templates

A preset record will contain a preset ID, name, element type, timestamps, and a normalized element blueprint.  Inserting a preset creates a new element ID and applies a safe insertion position; deleting or changing the source element never mutates an already saved preset.

Alternative considered: model a preset as a one-element document.  Rejected because it complicates insertion, page defaults, validation, and library presentation.

### 4. Introduce canonical page and element property normalization

The template contract layer will own defaults and validation for page settings, common element fields, type-specific `props`, and printable styles.  Inspector schemas remain UI metadata only: they must not become the source of truth for defaults or migration.  Load/import normalizes known aliases to canonical fields; serialization emits canonical fields only.

Alternative considered: have each inspector control write directly to arbitrary nested state.  Rejected because type drift would break runtime rendering and imports.

### 5. Use a field-capability registry for the property inspector

Each supported element definition will declare property groups, typed fields, ranges/enumerations, runtime effect, and optional cross-field validators.  The generic inspector will render this registry, while focused sub-editors remain responsible for structured values such as table columns and image source selection.  Errors are shown next to the field and block save/preview/print only when they make output invalid.

Alternative considered: continue growing a single schema file with component-specific conditionals.  Rejected because it makes validation, tests, and future element additions difficult to reason about.

### 6. Implement layout commands against selection bounds in document coordinates

Duplicate, align, and distribute commands will read selected unlocked/visible element boxes in millimetres, calculate changes against selection or page bounds, clamp results where required, and write one history transaction.  Ordering continues to use deterministic z-index normalization.  Runtime ignores editor selection state.

Alternative considered: use screen pixels from the canvas.  Rejected because zoom and pan would make saved geometry nondeterministic.

### 7. Treat independent design evidence as a release artifact

Every catalog item will have its source layout, visible copy, and any asset origin listed in the commercial-independence audit.  The release scan will include catalog definitions, i18n text, generated thumbnails, and JSON fixtures in addition to runtime source.

Alternative considered: rely on a manual review before release.  Rejected because similarity risks are easier to prevent with a repeatable audit trail.

## Risks / Trade-offs

- [Starter layouts resemble familiar business documents] → Use original geometry, copy, palette, and asset-free thumbnails; record the independent design rationale in the audit.
- [Property-model expansion breaks existing documents] → Default missing fields at load, migrate only documented aliases, and test load/save round trips from legacy fixtures.
- [Importing untrusted JSON causes oversized or malformed documents] → Enforce parse, schema, element-count, string-size, numeric-range, and supported-format limits before loading.
- [Large multi-selection operations hurt editor responsiveness] → Batch one document update and one history entry per command; test representative large selections.
- [More controls create runtime divergence] → Add a runtime effect assertion for every newly persisted field and cover preview/print parity in tests.
- [Local presets compete with user templates] → Keep separate libraries, labels, and data records; presets cannot carry page or document metadata.

## Migration Plan

1. Add normalizers and validators for canonical page/element properties behind the current template load/serialize boundary.
2. Add interchange parsing/export and element-preset repository APIs without changing existing saved template records.
3. Add catalog definitions and new-document UI; instantiate only into a new in-memory document.
4. Add inspector field groups and structured editors, routing all mutations through normalized document commands.
5. Add selection layout commands with history integration and tests.
6. Verify saved v1 documents, imports, presets, preview, and print against the same runtime contract; document release audit evidence.

Rollback: hide catalog, import/export, presets, or new inspector sections behind their feature entry points while retaining the existing normalized saved-document reader.  Existing saved templates remain loadable because unrecognized optional fields are ignored and missing fields receive defaults.

## Open Questions

- Should future REST repositories store element presets alongside templates or expose a separate endpoint?
- Is a customer-provided image URL sufficient for starter templates, or will an approved asset upload service be available later?
